## Yocto gotchas

### Disk space

A Yocto build easily eats **50 to 150 GB** per configuration (DL_DIR + sstate-cache + tmp). Some principles:

- **Externalize `DL_DIR` and `SSTATE_DIR`** on a dedicated disk, shared between all your projects — you factor out downloads and object caches.
  ```bash
  # In ~/.bashrc or ~/.zshrc, or via site.conf
  export DL_DIR="/data/yocto/downloads"
  export SSTATE_DIR="/data/yocto/sstate-cache"
  ```
- **The `tmp/` directory is not shareable** between projects and changes fast — put it on a fast SSD, not on a NAS/NFS.
- **Avoid encrypted home** (ecryptfs / LUKS on `~`) for `tmp/`: massive I/O penalty on millions of small files.

### Filesystem

- `tmpfs` for `tmp/` is tempting but requires 30+ GB of RAM; reserve for dedicated big-build machines.
- **No NFS for the build directory** — bitbake does heavy operations on xattrs and hardlinks that NFS handles poorly.
- **No spaces in BUILDDIR paths**.

### Performance

- **`ccache`**: add `INHERIT += "ccache"` to `conf/local.conf`. Massive gain on rebuilds.
- **`BB_NUMBER_THREADS` and `PARALLEL_MAKE`**: by default Yocto detects cores, but on powerful machines slightly lowering (e.g. `nproc - 2`) can avoid swapping on RAM-hungry packages (webkit, llvm…).
- **`rm_work`** in `INHERIT`: frees `WORKDIR` after build, saves tens of GB (but slows down post-build debugging).

### Locale and environment

- Bitbake refuses to run without `en_US.UTF-8` — auto-generated by the script.
- **Never** run bitbake as `root` (it refuses anyway).
- Source `oe-init-build-env` in every new shell (or wrap it in an alias).

## repo vs kas — which one to use?

| Criterion              | `repo`                              | `kas`                                  |
|------------------------|-------------------------------------|----------------------------------------|
| Format                 | XML manifest                        | YAML files                             |
| Generates local.conf   | No                                  | Yes                                    |
| Manages bblayers.conf  | No                                  | Yes                                    |
| One-shot build         | No (requires `bitbake` afterwards)  | Yes (`kas build project.yml`)          |
| Mandated by            | NXP, Xilinx, some BSPs              | More and more modern projects          |
| Containers             | Scriptable                          | Native integration (`kas-container`)   |

In practice, **kas** is more pleasant for starting a clean project. **repo** is mandatory as soon as you use a BSP that ships its manifest. Both are installed.

## Build inside a container — recommended option

To completely isolate the build from the host (and avoid surprises between Ubuntu/Yocto versions), two options:

- **`kas-container`**: official kas wrapper around Docker. `kas-container build project.yml` does everything.
- **`crops/poky`**: official Yocto Docker image. Useful for CI or unsupported Ubuntu versions.
  ```bash
  docker run --rm -it -v $PWD:/workdir crops/poky:ubuntu-22.04 \
      --workdir=/workdir -- bash
  ```

Docker is installed by the `06-containers` topic.

## Typical workflow (express summary)

```bash
# With repo (BSP shipping a manifest)
mkdir my-project && cd my-project
repo init -u https://github.com/vendor/manifests -b release-X
repo sync
source poky/oe-init-build-env
bitbake core-image-minimal

# With kas
kas checkout project.yml          # fetch layers only
kas build project.yml             # full fetch + build
kas shell project.yml             # shell with bitbake env ready

# Test an image in QEMU
runqemu qemux86-64 core-image-minimal

# Flash a .wic image to SD
bmaptool copy build/tmp/deploy/images/<machine>/image.wic /dev/sdX
```

## Going further

- **`devtool`** (ships with poky): excellent to modify an upstream recipe without touching the original layer (`devtool modify <package>`).
- **`oe-pkgdata-util`**: introspection of built packages.
- **eSDK** (`bitbake -c populate_sdk_ext`): extensible SDK to develop an app without rebuilding the full image.
